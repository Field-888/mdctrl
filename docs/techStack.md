## 1 目的与范围

本文回答技术层面的四个问题：

- 每个技术域选择什么方案；
- 为什么选择它，备选是什么；
- 需要核查哪些版本、许可证、维护状态与 API 能力；
- 验证未通过时回退到什么方案。

本文覆盖的技术域包括：

- 语言、工具链与工程基础；
- Markdown 解析、终端渲染、TUI 与编辑；
- 数学公式与 Mermaid；
- 存储、文档历史、索引与搜索；
- 文件监听与 Git 元数据；
- 通信、插件、Agent 与 MCP；
- 构建、测试、发布与供应链。

产品方向、用户场景与架构内容由 `vision.md` 与 `architecture.md` 承接；具体 crate 职责与实现细节由各 crate 技术文档承接。

本文只处理技术原料与支撑，产品与架构内容保持引用关系。

桌面核查已完成：版本、许可证、维护状态与 API 结论写入各技术域验证表；微型验证与集成验证留到实验分支。

桌面核查环境：Rust/Cargo 1.99.1、Git 2.43.0、Node 24.19.0、SQLite 3.45.1、Windows Terminal/WSL。

## 3 语言与工程基础

### 3.1 语言与工具链

选择 Rust stable。原因包括：

- 终端控制、字节级解析、布局计算与索引需要可预测的性能；
- 单二进制分发适合命令行工具；
- 类型系统与错误处理适合长期维护的 CLI / TUI 项目；
- 生态覆盖解析、终端、索引、序列化、测试与打包。

工具链策略：

- 固定 stable toolchain，并声明 MSRV；
- 使用 `rust-toolchain.toml` 固定开发与 CI 环境；
- 依赖版本锁定，升级通过 PR 与 CI 验证；
- 优先稳定特性与可维护性。

### 3.2 并发与错误

- 核心路径使用线程与 channel：扫描、索引、监听、渲染准备作为独立任务；
- 渲染与输入循环保持同步、可预测；
- 异步运行时用于网络、流式输出与 Agent/MCP；
- 库使用 `thiserror` 定义结构化错误，二进制使用 `anyhow` 汇总；
- 使用 `tracing` 记录结构化日志，日志写入本地状态目录。

### 3.3 构建与依赖

- 发布构建启用 LTO、strip 与优化级别；
- 重依赖使用 feature gate；
- 使用 `cargo bloat` 观察体积来源；
- 使用 `cargo-deny` 审计许可证与依赖；
- 启动时延迟初始化语法高亮、索引、网络与 Agent 组件。

## 4 Markdown 解析

### 4.1 技术需求

- CommonMark 与 GFM 常用语法；
- AST 节点携带源位置，服务跳转、诊断、编辑与 diff；
- frontmatter、任务列表、表格、脚注、callout 等扩展；
- 数学公式、Mermaid、wiki 链接等自定义语法扩展点；
- 畸形输入稳定处理。

### 4.2 候选

| 候选 | 优势 | 风险 |
| --- | --- | --- |
| `comrak` | GFM 覆盖好，支持源位置，扩展选项多，生态成熟 | AST 类型自有，复杂扩展需要适配 |
| `markdown`（markdown-rs） | mdast 模型清晰，位置信息完整，现代 | 生态相对年轻，扩展与性能需要核查 |
| `pulldown-cmark` | 性能好，事件流简单，偏移量支持 | 语义 AST 与完整源映射需要额外工作 |

### 4.3 选择

**`comrak` 作为默认解析器**，`markdown` 作为备选，`pulldown-cmark` 作为观察项。

选择理由：

- GFM、sourcepos 与扩展覆盖满足当前需求；
- math、callout、frontmatter、wikilink、footnote 等扩展已有官方支持；
- 默认 features 包含 `cli`、`syntect-onig`、`bon`，作为库使用时关闭默认 features；
- 先完成端到端链路，复杂语法通过适配层补齐。

解析器输出进入文档模型层；具体模型与布局由 crate 技术文档承接。

## 5 终端渲染与 TUI

### 5.1 TUI 与布局

- TUI 选择 `ratatui` + `crossterm`；
- 备选 `cursive` 0.21.1，观察自绘终端层；
- 布局、换行、表格与 Cell Grid 自研；
- 宽度计算使用 `unicode-width` 与 `unicode-segmentation`；
- 语法高亮使用 `syntect` + `two-face`；
- 终端图片协议通过 `ratatui-image` 做原型，布局整合与缓存自研。

### 5.2 文本缓冲与编辑

- 文本缓冲选择 `ropey`，编辑层自研；
- 支持大文档、撤销、选择、CJK 输入与源位置映射；
- 外部编辑器作为复杂编辑的补充路径；
- 编辑与渲染共享源位置，光标与布局保持一致。

### 5.3 终端能力

- 颜色、背景色、同步输出、图片协议、字体与宽度通过探测与回退处理；
- OSC 11 背景探测失败时使用默认主题；
- 终端测试使用可记录输出的后端，关键交互补手工验证。

## 6 数学公式与 Mermaid

### 6.1 数学公式

默认路线：**MathJax 主路线，Typst 备选，原生文本作为行内与回退方案。**

| 路线 | 优势 | 代价 |
| --- | --- | --- |
| MathJax | LaTeX 兼容自然，输出 SVG，生态成熟 | 需要 Node 运行时 |
| Typst | Rust 生态，数学质量高，可输出 SVG | 需要额外工具链与 LaTeX 转换 |
| 原生文本布局 | 零外部依赖，行内友好 | 复杂公式表达受限 |
| 系统 LaTeX | 排版质量高 | 依赖重，平台覆盖有限 |

链路：

```text
公式源码 → MathJax / Typst → SVG → 栅格化 → 终端图片
```

行内简单公式使用文本近似；行间与复杂公式走图片链路；图片协议缺失时回退文本或源码。

### 6.2 Mermaid

默认路线：**`mermaid-cli` 主路线，源码与占位回退。**

- `mermaid-cli` 输出 SVG；
- SVG 栅格化后走终端图片协议；
- 渲染结果按内容哈希缓存；
- 外部服务作为观察项；
- 原生 Rust 实现作为长期观察项；
- Puppeteer 与 Chromium 作为 peer 依赖安装，进入发布文档。

### 6.3 终端图片

- 支持 kitty、sixel、iTerm2 与半块字符；
- 处理单元格尺寸、缩放、行高与滚动；
- 资源就绪前显示占位，就绪后通过事件替换；
- 外部渲染器使用子进程隔离、超时与资源限制。

## 8 索引与搜索

### 8.1 索引

- 使用 SQLite FTS5；
- 索引保存全文、路径、标题与元数据字段；
- 增量更新使用文件元数据与内容指纹；
- 索引可以删除重建；
- Tantivy 作为独立搜索备选。

### 8.2 中文检索

默认方案：**SQLite FTS5 + `libsimple` 的 `simple` tokenizer**。

`libsimple` 提供中文、英文与拼音分词，查询使用 `jieba_query` 或 `simple_query`。分词器通过 auto-extension 注册，词典资源随发行包分发；版本、许可证与 rusqlite 范围见验证表。

备选方案：**`tantivy` + `tantivy-jieba`**。

`tantivy-jieba` 以独立搜索引擎完成中文分词与检索，适合 SQLite tokenizer 集成成本偏高时切换。

回退方案：**FTS5 trigram + 查询扩展**。

桌面实测显示 trigram 对三字及以上中文查询有效，两字查询需要额外扩展。`sqlite-jieba-tokenizer` 作为观察项，其版本基线基于 rusqlite 0.38。

排序采用 BM25 与字段权重，路径权重作为补充。

### 8.3 模糊查找

文件名与路径查找使用 `nucleo`，MPL-2.0，已接受该许可证；发行时保留 MPL-2.0 声明与 NOTICE 记录。备选 `fuzzy-matcher`，版本与许可证见验证表。

### 8.4 验证状态

## 10 通信与插件技术

### 10.1 通信编码

- 进程内使用 typed 消息；
- 本地 IPC 使用 JSON 与长度前缀 framing；
- 远程连接复用 JSON 语义，传输实现后续选择；
- 大资源使用句柄或文件路径，避免大块内联。

### 10.2 插件技术

- 外部插件使用 JSON-RPC over stdio；
- manifest 描述入口、能力、权限与版本；
- 进程启动、握手、命令注册、健康检查与退出；
- 插件异常隔离在单个进程；
- 插件返回结构化视图，视图序列化格式由协议层定义；
- 插件安装、列表、移除与诊断使用独立命令。

权限在 manifest 中声明，宿主在调用时校验：

| 能力 | 含义 |
| --- | --- |
| workspace.read | 读取工作区文档 |
| workspace.propose | 提交写入提案 |
| command.invoke | 调用命令总线 |
| network.access | 访问网络 |

## 13 验证策略

技术验证分三层：

| 层级 | 内容 | 产物 |
| --- | --- | --- |
| 桌面核查 | 版本、许可证、维护状态、平台支持、API 能力 | 写回各技术域的验证状态表 |
| 微型验证 | 小型原型、夹具、脚本 | 结论与回退选择 |
| 集成验证 | 真实实现、真实语料、真实终端 | 性能、质量与稳定性结论 |

规则：

- 每个技术域维护自己的验证状态表；
- 桌面核查结论写在对应技术域，保持单一位置；
- 未完成微型验证的项目保留“待微型验证”，并写明默认方案与回退；
- 集成验证项在真实实现阶段完成；
- 技术文档发布前完成所有桌面核查，当前桌面核查已完成；
- 产品范围与优先级问题由 `devPlan.md` 承接。
