## 1 目的与范围

本文定义 mdctrl 当前阶段的 MVP 切分、依赖顺序、分工、质量要求与内部发布边界。

本文覆盖：

- 五个 MVP 的主路径、范围与验收；
- MVP 之间的依赖与推进顺序；
- crate 主责与阶段角色；
- 质量标准与功能冻结；
- 内部发布条件。

阶段过程、文档目录与角色规则由 `devMode.md` 承接；产品方向由 `vision.md` 承接；技术结构由 `architecture.md` 承接；技术选型由 `techStack.md` 承接。

## 2 目标与约束

- 本次开发采用五个 MVP 的阶段顺序，每个阶段交付一条端到端用户路径。
- 范围保持固定，时间保持弹性；阶段按出口条件结束，具体节奏由团队投入与验证结果决定。
- 团队并行，成员内部按设计、实现、自测、交付的顺序推进。
- MVP5 是内部可用版本；公开版本在内部稳定后另行规划。
- 数学公式与 Mermaid 做有限支持，放在 MVP2；完整覆盖进入后续规划。
- 功能冻结在 MVP4 之后；MVP5 聚焦打包、文档、性能基线、缺陷修复与内部发布。
- 范围、顺序或冻结规则的实质变更由三人确认并记录。

## 3 范围边界

| 类别 | 内容 |
| --- | --- |
| 必须完成 | 五个 MVP 的主路径、测试、文档、打包与内部发布 |
| 有限支持 | 数学公式、Mermaid、终端图片；支持矩阵与降级路径作为交付的一部分 |
| 后续规划 | GUI、WebUI、插件市场、通用 agent 框架、完整数学/Mermaid、公开版本 |

当前终点覆盖：

- 基础阅读、检索、链接与反链；
- 公式、Mermaid、健康检查与 Agent 审阅；
- 编辑、Agent 写作与文档历史；
- 插件、命令总线与 CLI 自动化；
- 安装、文档与内部发布。

公开版本的范围、时间与支持策略在内部稳定后单独规划。

## 4 五个 MVP

### 4.1 MVP1 基础阅读与检索

**主路径**：在仓库中找到文档并读懂基础内容。

**范围**：

- 工作区扫描、文件树、路径与忽略规则；
- 协议、kernel、文档模型、基础布局、TUI 阅读；
- GFM、表格、代码、引用、callout、frontmatter；
- 主题、CJK、宽字符与终端宽度；
- 模糊文件名查找、全文索引、中文检索；
- 链接、反链与跳转；
- CLI 打开与基础输出；
- 公式与 Mermaid 显示源码或占位，进入 MVP2 后升级。

**验收**：

- 在真实仓库完成“找—读—跳转”；
- 中文两字与多字查询可用；
- 基础 GFM、CJK、表格、代码与主题稳定；
- 快照、索引与 CLI 测试通过；
- 基础 CI 与阶段文档完成。

**说明**：MVP1 同时建立协议、kernel、render、TUI、workspace 与 index 的基础，是五个 MVP 中范围最宽的一个。

### 4.2 MVP2 深度阅读与审阅

**主路径**：打开一篇复杂文档，看懂图表，发现健康问题，并让 Agent 给出审阅意见。

**范围**：

- 行间公式、简单行内公式、常见 Mermaid 图表；
- 终端图片协议、媒体缓存与降级；
- 断链、孤儿、过期、缺失元数据；
- TUI 健康面板、`check` CLI 与退出码；
- 内置 Agent 的摘要、分析、审阅工作流；
- provider 抽象、上下文装配与只读 MCP；
- Agent 建议以报告或差异呈现，写入进入 MVP3。

**验收**：

- 公式与 Mermaid 有支持矩阵、缓存与降级；
- 示例仓库中的四类健康问题与期望清单一致；
- Agent 基于文档、反链、健康与历史给出摘要与审阅建议；
- MCP 客户端可以只读查询文档、搜索、健康与反链；
- 阶段文档与测试证据完成。

**说明**：MVP2 包含图表、健康与 Agent 审阅三条并行工作线，阶段内按任务 owner 分工推进。

### 4.3 MVP3 编辑与写作

**主路径**：修改文档，或让 Agent 起草并审批后落盘。

**范围**：

- 渲染态热编辑、源码切换、撤销；
- 外部编辑器、热重载；
- 文档历史更新；
- Agent 写文档工作流；
- diff 预览、接受、拒绝、局部采纳；
- 写入版本检查与冲突提示；
- 溯源信息。

**验收**：

- 手动编辑与 Agent 写作两条路径都能完成“修改—审批—保存”；
- 文档历史与写入结果一致；
- 冲突场景提示并保留原内容；
- 写入保留来源、模型与时间；
- 阶段文档与测试证据完成。

### 4.4 MVP4 扩展与自动化

**主路径**：安装插件，并通过命令完成文档任务。

**范围**：

- 命令总线；
- 插件协议、manifest、能力与权限；
- 插件安装、列表、移除、诊断；
- 示例插件与故障测试插件；
- 插件崩溃、超时与非法消息隔离；
- 插件返回结构化视图；
- CLI 自动化输出。

**验收**：

- 示例插件可安装、运行、卸载；
- 插件命令与官方命令走同一套总线；
- 插件异常隔离在单个进程；
- CLI 输出可被脚本与 agent 使用；
- 阶段文档与测试证据完成。

### 4.5 MVP5 内部可用

**主路径**：从零安装，并在真实仓库中日常使用。

**范围**：

- `.deb` 与 tarball；
- 干净 Linux/WSL 环境安装验证；
- 用户手册、安装说明、插件指南；
- 性能基线与明显瓶颈优化；
- 已知限制与降级说明；
- 内部发布清单。

**验收**：

- 干净环境安装成功；
- 团队可以连续日常使用；
- 文档、示例与当前行为一致；
- 阻断级缺陷关闭；
- 内部发布清单完成。

**说明**：MVP5 聚焦交付与稳定，用户路径沿用前四个 MVP。

## 5 依赖与顺序

```text
MVP1 基础阅读与检索
  ├── MVP2 深度阅读与审阅
  │     └── MVP3 编辑与写作
  └── MVP4 扩展与自动化

MVP1～MVP4
  └── MVP5 内部可用
```

推荐顺序为 MVP1 → MVP2 → MVP3 → MVP4 → MVP5。

MVP3 依赖 MVP2 的 Agent provider 与审阅能力；MVP4 依赖 MVP1 的协议与命令基础，可以在 MVP2、MVP3 期间完成接口协商，再进入正式阶段。

## 6 分工与角色

### 6.1 crate 主责

| crate / 范围 | 主责 | 模块 owner |
| --- | --- | --- |
| `mdctrl-protocol` | `field` | 全员评审 |
| `mdctrl-core` | `field` | `ylgd0915` 参与 workspace/history 领域语义 |
| `mdctrl-render` | `field` | `silkage15` 参与 View 消费 |
| `mdctrl-server` | `ylgd0915` | `silkage15` 负责 plugin/transport；`ylgd0915` 负责 agent/MCP；`field` 负责 media |
| `mdctrl-tui` | `silkage15` | `field` 参与 View 契约；`ylgd0915` 参与搜索/健康界面 |
| `mdctrl-cli` | `silkage15` | `ylgd0915` 提供 check/index 数据命令；`field` 参与协议 |

server 内部模块：

| 模块 | owner |
| --- | --- |
| workspace store、history、index、health、git | `ylgd0915` |
| agent host、MCP host | `ylgd0915` |
| media | `field` |
| plugin host、transport | `silkage15` |
| server 组合根 | `ylgd0915` |

打包、发布与 CI 由 `silkage15` 主责；用户手册与插件指南由 `silkage15` 汇总；`field` 负责架构评审，`ylgd0915` 确认数据与 Agent 能力。

以上为书面分工。实际执行中，阶段 manager 可以按任务、接口与负载灵活调整；调整记录在阶段说明或会议记录中。

### 6.2 阶段角色

阶段 manager 按阶段轮换：`field` → `ylgd0915` → `silkage15` → 循环。

- 阶段 manager：阶段文档、接口协商、集成节奏、阶段会议与总结；
- 任务 owner：设计、实现、自测、文档与 Agent 指导；
- 测试执行人：验收、端到端与手工测试，默认由任务 owner 担任，阶段 manager 可以指定代理；
- 评审人：非作者代码与文档评审，跨模块接口由使用方参与。

阶段末端到端测试由阶段 manager 指定非主责成员执行。

## 7 质量标准与功能冻结

每个 MVP 按 `devMode.md` 的阶段门禁执行：

- 阶段任务达到完成定义；
- `docs/MVPn/` 的阶段说明、设计、接口与测试文档更新；
- 端到端路径演示通过；
- 测试执行人记录测试结果与证据；
- 无重大功能缺陷；
- 阶段会议完成，阶段总结与下一阶段输入明确。

MVP4 完成后进入功能冻结。MVP5 聚焦：

- 打包与安装；
- 用户手册与插件指南；
- 性能基线；
- 缺陷修复；
- 内部发布。

功能冻结后的变更按缺陷、文档或发布阻塞处理；新需求进入后续规划。

## 8 版本与发布

### 8.1 版本号

项目采用语义化版本 `MAJOR.MINOR.PATCH`。版本号在 `[workspace.package]` 统一维护，所有 crate 继承同一版本。

开发阶段使用 `0.MINOR.PATCH`：

- `MINOR` 对应 MVP 编号，MVP1 为 `0.1.x`，MVP2 为 `0.2.x`，依此类推；
- MVP 启动时将 `MINOR` 设为该阶段编号，`PATCH` 归零；
- 阶段内的缺陷修复与内部优化递增 `PATCH`；
- 预发布版本使用 `-alpha.N`、`-beta.N`、`-rc.N`；
- 发布标签使用 `vX.Y.Z`；
- 版本号在打标签或发布时递增，日常提交保持当前版本。

首个公开稳定版本为 `1.0.0`。此后按 SemVer 递增：

- `MAJOR`：不兼容的协议、接口或行为变更；
- `MINOR`：向后兼容的新功能；
- `PATCH`：向后兼容的修复与内部优化。

MVP 编号与 `MINOR` 的对应关系在 `0.x` 阶段使用，进入 `1.0.0` 后结束。

### 8.2 内部发布

MVP5 成为内部可用版本。内部发布条件：

- 干净 Linux/WSL 环境安装成功；
- 团队可以连续日常使用；
- 阅读、检索、检查、编辑、插件与 Agent 主路径可用；
- 用户手册、插件指南与安装说明完成；
- 已知限制与降级行为有文档；
- CI 与测试证据完整。

### 8.3 公开版本

公开版本在内部稳定后单独规划，前置条件包括：

- 更长时间的真实仓库试用；
- 多终端兼容性测试；
- 性能、内存与启动优化；
- 安全审查与依赖审计；
- 文档、示例与社区文件完善；
- 支持范围、弃用策略与发布节奏明确。
