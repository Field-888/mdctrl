## 1 项目定位

mdctrl 面向把文档放在代码仓库中的开发团队，服务需要长期维护项目文档的协作场景。团队把 README、设计文档、ADR、RFC、运维手册放在仓库里，文档与代码一起演进；mdctrl 为这些文档提供统一的工作空间。

它把文档视为持续维护的资产。文档从创建、被引用、更新到退场，都在同一个工作空间里被看见和处理；阅读、发现、治理、编辑与 agent 协作围绕同一份文档状态展开。

## 2 为什么需要 mdctrl

### 2.1 终端里的 Markdown 阅读体验仍有提升空间

终端是许多开发者的主工作区。代码、命令、日志和文档都在同一个窗口里，切换成本很低；文档却常常要求读者离开终端，打开浏览器或编辑器。

现有工具能够把 Markdown 显示出来，排版、层级与长文阅读体验仍然粗糙。标题、段落、列表和代码块依赖颜色区分，表格与宽字符容易错位；长文档缺少稳定的阅读节奏，读者很难持续读下去。结果往往是快速扫一眼、复制几段，再回到编辑器里继续工作。

受 OpenCode 等终端工具的启发，终端阅读可以兼顾清晰的层级、稳定的版式与顺手的交互，读者对终端内的阅读体验有了更高期待。

### 2.2 文档散落在仓库各处

项目文档分布在 README、`docs/`、ADR、RFC、运维手册和各个模块目录中。目录结构反映代码组织，文档之间的关系却跨越目录；文件名、标题和链接各自表达一部分信息。

查找文档依赖 `find`、`grep` 和记忆。读者知道关键词，却未必知道文档在哪个目录；知道文档存在，却未必记得它的标题。找到文档后，读者还要在文件管理器、编辑器和终端之间切换，才能打开、阅读和继续查找。

团队需要在一个统一的工作视角里发现、打开和阅读文档。这个视角既要呈现仓库结构，也要呈现文档之间的引用关系；既要服务直观操作，也要服务脚本和 agent。

### 2.3 文档缺少生命周期与关系

每次迭代，文档都要靠人回忆哪些内容受影响。修改一个接口，可能同时影响 ADR、设计文档、运维手册和 README；这些关系记录在链接、引用和元数据里，却分散在不同文件中。

文档之间的引用关系、归属和新鲜程度散落在文档中，查看时需要逐篇打开。维护者要判断哪些文档需要更新，只能靠记忆、搜索或逐个检查；失修的文档容易长期潜伏。

文档创建后缺少持续追踪。文档写完就进入仓库，后续是否被引用、是否仍然准确、由谁负责，往往没有统一答案；时间一长，文档与代码脱节，读者只能凭经验判断哪些内容可信。

### 2.4 阅读与编辑是割裂的

读到需要修改的地方，读者要退出渲染器、打开编辑器，再回到原位置；或者直接面对源码。阅读与修改被拆成两段流程，上下文容易丢失。

小改动尤其明显。修正一个错别字、补一句说明、更新一个链接，都要经历“找到位置—退出—打开—修改—保存—回到原处”的过程；成本高到让人倾向于推迟，文档因此逐渐失修。

阅读与编辑共享同一份文档状态，却使用不同的工具和界面。读者需要在两种心智模型之间切换：一种关注内容与结构，一种关注源码与语法。

### 2.5 人与 agent 的协作方式正在变化

agent 已经能发现、阅读并改写仓库里的文件。它可以在一次会话里扫描目录、理解代码、生成文档初稿，也可以根据反馈修改内容。

文档领域的链接、关系和生命周期缺少稳定接口。agent 只能临时推断文档之间的关系，重复扫描目录、解析链接、猜测哪些内容过期；每次任务都从零开始，结果难以复用。

人和 agent 的文档操作也缺少共同的命令与状态接口。人看到的是界面与快捷键，agent 看到的是文件与文本；双方对“哪些文档受影响”“哪些修改已批准”缺少一致视图。

## 3 产品模型

mdctrl 由三个部分构成：文档网络、三个入口、可组合能力。

### 3.1 文档网络

文档网络以仓库中的 Markdown 文件为节点。每份文档的路径、标题、frontmatter 与正文共同描述它的身份；链接、引用与元数据构成文档之间的边。

边有两种来源。显式链接来自正文中的相对链接、锚点与引用；隐式关系来自元数据中的归属、标签、复查时间与关联文档。两者合在一起，形成一张可查询的文档关系图。

每个节点有生命周期。文档从创建、被引用、更新，到过期、归档，状态随项目迭代变化；mdctrl 在读取与索引时维护这些状态，并把异常放回网络中。文档通过链接或索引进入网络。

### 3.2 三个入口

TUI 面向直观浏览与编辑，适合读者在终端里完成日常阅读、检索和修改。

CLI 面向脚本、批量和自动化，提供可组合的命令、结构化输出与明确退出码。

agent 接口面向 agent 协作，把文档、链接、关系与生命周期暴露为可查询的状态。

三个入口共享同一套命令与能力，差异体现在交互方式。TUI 提供可视化与键盘操作，CLI 提供可组合的机器接口，agent 接口提供稳定的状态与操作契约。

### 3.3 可组合能力

阅读、检索、治理、编辑与 agent 工作流以可组合的方式提供。每项能力有清晰的输入、输出与边界，可以独立使用，也可以组合成更完整的工作流。

能力可以按需加载、替换和扩展。团队可以只启用阅读与检索，也可以加入健康检查、编辑与 agent；每项能力通过清晰接口组合，形成适合团队的工作流。

### 3.4 与现有工具的关系

Git 管理仓库中的全部文件与版本历史，提供工作树、提交、分支与差异。mdctrl 聚焦其中的 Markdown 文档，读取与文档相关的状态、历史与差异，把版本信息用于文档生命周期与变更提示。

编辑器负责单篇文档的文本修改，CI 负责构建、测试与质量门禁。mdctrl 负责文档之间的关系、生命周期与阅读体验，把这些工具串联到文档工作流里。

## 4 为谁而做

### 4.1 终端型开发者

他们的工作重心在命令行与终端。读设计文档、查接口说明、改一段说明，都希望在当前窗口里完成；切换到浏览器或编辑器会打断正在进行的任务。

他们需要快速找到文档、连续阅读长文、在阅读现场做小修改，并且保持键盘操作与终端工作流。一次完整的阅读与修改能在同一个工作流里完成，是 mdctrl 对他们的价值标准。

### 4.2 项目维护者

他们负责一个仓库的文档质量：文档之间的关系是否仍然成立、内容是否仍然准确、责任是否明确，都是日常需要回答的问题；这些问题跨越目录、跨越文档类型，靠人工检查很难持续。

他们需要看到文档网络的状态，知道文档之间的关系、准确性与责任归属。mdctrl 对他们的价值，是让这些状态成为日常可见的工作对象，并在迭代中及时处理。

### 4.3 Agent 与自动化工具

agent 通过 CLI、MCP 和稳定接口操作文档。它需要可预测的命令、稳定的输出约定和明确的写入边界，才能在无人值守或半自动流程中可靠工作。

agent 还需要理解文档之间的关系与生命周期，避免只改一篇文档却遗漏相关引用。mdctrl 对他们的价值，是让 agent 与人类工作流协同完成文档操作，共享同一份文档状态与审批规则。

## 5 预期能力

### 5.1 阅读与呈现

mdctrl 提供正确的 Markdown 解析和终端排版。标题层级、段落间距、列表缩进、引用、callout、代码块、表格、链接与分隔线按照统一规则呈现；CJK 与宽字符按显示宽度计算，长文档保持稳定的阅读节奏。

mdctrl 提供多套主题，适应不同终端背景与个人偏好。主题通过语义 token 控制前景色、背景色、强调色、边框与代码配色；终端背景变化时，主题可以自动切换。

数学公式与 Mermaid 是重点能力。mdctrl 提供可读的终端显示：行间公式优先使用高质量渲染，行内简单公式使用文本近似；常见 Mermaid 图表优先渲染，其他图表显示源码或占位。终端能力不足时，显示方式自动降级，支持矩阵与限制在文档中说明。

### 5.2 文档网络与治理

mdctrl 在文档网络上提供检索与导航。读者可以按文件名、路径、标题、标签与正文内容查找文档，也可以沿链接、反链与相关文档继续浏览。

mdctrl 维护文档的生命周期。状态、归属、复查时间与关联信息来自元数据，文档的创建、更新、过期与归档状态随项目迭代变化。

mdctrl 提供异常检测。断链、过期、孤立、无人维护等状态被收集、分类并展示；维护者可以从网络视图看到关系与异常，并据此安排文档更新。检查结果可以通过 CLI 输出，接入 CI 与日常流程。

### 5.3 交互与编辑

TUI 提供三栏浏览、状态栏、命令面板和长文档阅读。文件树呈现仓库结构，正文区保持稳定排版，侧栏展示大纲、反链、健康状态或 agent 结果；键盘操作覆盖浏览、搜索、跳转与命令执行。

CLI 提供打开、搜索、检查、索引等命令，覆盖脚本、CI 与 agent 的常用操作。

渲染态热编辑让修改留在阅读现场。读者可以在渲染视图中修改当前块或段落，随时切换源码视图，保存后立即看到结果；外部编辑器与热重载作为补充路径，覆盖更复杂的编辑场景。

### 5.4 扩展机制

插件系统支持命令、数据源、导出器与视图扩展。插件可以注册新命令、接入外部文档源、导出 Markdown 或 HTML、提供自定义面板；插件能力与官方能力使用同一套命令与状态模型。

插件宿主提供安装、列表、移除、诊断与故障隔离。插件以独立进程运行，崩溃、超时或非法消息影响单个插件，主程序继续工作；manifest 描述能力、权限与入口，宿主据此完成加载与校验。

### 5.5 Agent 协作

mdctrl 提供最小内置 agent 与只读 MCP。内置 agent 直接在 TUI 中工作，MCP 让外部 agent 客户端查询文档、搜索、健康状态与反链。

agent 围绕三套工作流展开。写文档从代码、上下文与已有文档形成初稿，经人审阅后落盘；分析文档理解结构、内容与健康状态，给出摘要与改进建议；审阅文档发现不一致、过期、链接与表达问题，形成可执行的修改建议。

agent 的写入经过审批。每次修改先生成差异，人可以选择接受、拒绝或局部采纳；写入保留来源、模型与时间等溯源信息。只读 MCP 先覆盖查询能力，写入能力在审批与权限机制完善后开放。

## 6 设计原则

- **一切皆 Markdown**：Markdown 文件是文档的唯一记录，frontmatter、正文与链接都保存在文件中。索引、缓存与关系图从文件派生，可以随时重建；文件本身始终是事实来源。
- **零迁移接入**：mdctrl 直接指向已有仓库目录，文档保持原路径、原格式和原有构建方式。团队接入时只需安装与配置，现有文档结构继续工作。
- **约定优先于配置**：大部分行为由默认约定决定；frontmatter 可选，缺失时仍能浏览、索引与检查。需要定制时再用配置覆盖，降低接入成本。
- **排版纪律**：排版质量来自统一的间距、色彩、宽度与层级规则。规则集中管理，主题只改变视觉 token，阅读节奏保持稳定。
- **单一命令总线**：键盘、命令面板、CLI、插件与 agent 通过同一套命令表达操作。新增能力在命令总线上注册，所有入口获得一致行为。
- **写入必须审批**：插件与 agent 对文档的修改先生成差异，经人确认后写入。每次写入保留来源与操作记录，支持拒绝、局部采纳与回滚。
- **能力不足时降级**：终端能力、图片协议或外部渲染器不足时，mdctrl 自动选择可读的替代显示。核心阅读路径始终可用，降级状态对用户可见。
- **协议式解耦**：前端与核心通过稳定协议通信，TUI、CLI、未来 GUI/Web 共享同一套能力。协议先于界面实现，新增前端复用核心能力。
- **扩展优先**：核心维护稳定的基础协议，新能力优先以插件形式交付；插件拥有独立的发布节奏。

## 7 长期前景

当终端场景稳定之后，mdctrl 可以向更远的方向探索。这些方向建立在现有文档模型、命令总线与插件机制之上，分阶段推进。

### 7.1 跨端体验

mdctrl 从终端扩展到 Windows GUI 与 WebUI。GUI 提供更直观的浏览、编辑与可视化关系图，WebUI 提供轻量的远程访问与分享；Windows 与 WSL 之间通过统一协议协同，让不同工作环境共享同一套文档能力。

终端、GUI 与 Web 看到同一份文档状态，操作通过同一套命令执行；用户可以在不同设备与工作环境之间切换，文档能力保持一致。

### 7.2 更完善的 agent 支持与通用 agent 工作台

agent 更深地参与文档的生成、分析与审阅。它可以在一次任务中读取相关文档、理解链接关系、提出多篇文档的联动修改，并根据人的反馈迭代。

当核心能力稳定之后，mdctrl 演进为更通用的 agent 工作台。能力通过插件组合生长，agent 可以调用文档、搜索、健康检查、编辑与外部工具；人保留目标、边界与写入审批。

### 7.3 插件市场与生态

围绕插件、主题、模板与工作流形成社区生态。第三方可以发布命令插件、文档源适配器、导出器、视图与主题，团队按需组合自己的文档工作台。

插件市场提供发现、安装、版本管理与安全信息。官方维护核心能力与协议，社区贡献扩展与模板；生态建立在稳定的插件接口、权限模型与质量规范之上。
